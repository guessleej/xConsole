# 多工作站管理規劃（核心）

2026-11-07定案範圍。本檔是公開核心這一側的真本：每一項做完把狀態改成「完成」並寫上PR。
企業版模組（閉源）的規劃在私有repo `xConsole-Enterprise` 的 `docs/PLAN.md`，本檔只寫核心要提供的機制與兩邊的介面合約。

## 版本名稱

| 版本 | 名稱 | 說明 |
|---|---|---|
| 個人版 | xConsole Personal | 桌面安裝檔、管一台。它是開源核心的一種使用方式，不另開repo |
| 企業版 | xConsole Enterprise | 閉源模組，內含教育包與企業包，放在私有repo `xConsole-Enterprise` |

開源repo維持 `guessleej/xConsole` 不改名：線上更新（`console/updater.py` 的 `REPO`）寫死問這個位置，已安裝的個人版都靠它更新。

## 一、要解決的情境

| 情境 | 規模 | 機型 | 誰在管 | 誰在用 |
|---|---|---|---|---|
| 個人（xConsole Personal） | 1台 | 任何電腦 | 自己 | 自己 |
| 學校電腦教室 | 一間20台，全校數間 | 5090桌機、AI 395、MIC-743、DGX GB10混搭 | 老師管自己那間，資訊組看全校 | 學生，多人輪流用同一台 |
| 企業 | 數十到數百台 | 同上，另有AI 395筆電；MIC-743多在產線 | IT管全公司，部門主管看自己部門 | 員工，多半一人一台 |

個人版（xConsole Personal）維持現狀，本規劃不動它。學校與企業情境要搭配企業版（xConsole Enterprise）。機器只有「加入群組」之後才受管，退出群組就回到個人版。

這些機器是**工作站，不是伺服器**。規劃全部以這幾件事為前提：

- 每天開關機，筆電會休眠、會被帶回家。
- IP由DHCP配，會變。
- Windows防火牆、公用網路設定擋住連進來的連線（HP實測過：公用網路下別台連不到9400）。
- 學校常裝還原卡，重開機就還原系統碟；派送時多半用同一份映像複製。
- 前面坐著人，瀏覽器、Office、IDE都在吃記憶體。

現在的設計是主控台連到固定位址的代理，當場下指令。這套適合機房，搬到工作站上會一路卡住。

## 二、角色與動線

照實際使用的順序排，最常做的放最前面。

**老師／IT（管理者）**

| 步驟 | 做什麼 | 前一步 | 做完去哪 |
|---|---|---|---|
| 1. 建群組 | 在主控台建「三樓電腦教室」或「研發部」 | 主控台已安裝並登入 | 產生群組加入碼 |
| 2. 加入機器 | 把加入碼帶進安裝程式（手動、映像、Intune／SCCM派送皆可） | 有加入碼 | 群組總覽看到機器陸續上線 |
| 3. 設定群組 | 選模型、上下文、思考開關、鎖定哪些項目、保留多少記憶體給使用者 | 至少一台上線（才知道有哪些機型） | 看每種機型會拿到哪一版、大概多快 |
| 4. 準備模型 | 按「準備」，各台開始從同群組或內部鏡像取得模型 | 群組設定已存 | 就緒狀態逐台變綠 |
| 5. 套用 | 立即、下次開機或排定時間套用 | 模型就緒（未就緒的機器會等到就緒才套用） | 群組總覽顯示「N／M台已套用」 |
| 6. 日常 | 看就緒、看誰離線、處理「放不下」與「設定不同」 | 已套用 | 出使用報告 |

**使用者（學生／員工）**

打開桌面安裝的xConsole就能用，畫面和個人版相同。受管的項目在設定裡標示「由〇〇管理」，按鈕停用並說明找誰；沒鎖的項目照樣可以改。

這件事現在還做不到，要靠第三節第11點補上：現行桌面App一律自己另外帶起一支私有代理（`desktop/src-tauri/src/main.rs` 的 `spawn_agent()`），受管機器上那支以SYSTEM執行的代理它看不到，畫面也就反映不了群組的鎖定與政策。

**群組頁的設定順序軸**（放在頁面最上方，狀態由真實資料算出）：

1. 加入機器：至少一台在線
2. 設定群組：已存一版群組設定
3. 準備模型：所有在線機器的模型都已就緒，或已標示「放不下，改用X」
4. 套用：所有在線機器的已套用版本等於最新版
5. 檢查：沒有「設定不同」與「需要重新加入」的機器

## 三、核心功能

### 1. 代理主動連回主控台

**做法**：代理開機後主動以HTTPS長輪詢連回主控台。

- `POST /api/agent/poll`：帶節點權杖，主控台最多掛25秒，有指令就立即回。一次可以回多筆。
- `POST /api/agent/result`：送回執行結果。

選長輪詢不選WebSocket，是因為代理只用Python標準函式庫，沒有第三方相依。

- **上層程式不動**：`call_node()` 依節點的 `link` 決定走法。`pull` 是現行的主控台連代理，伺服器照舊用這個；`push` 把指令排進那台的佇列，等結果回來，簽名與回傳值都不變。換模型、准入、模型庫這些頁面不必改。
- **每筆指令都有編號**：現行主控台會對同一台同時發好幾個呼叫，例如換模型最長等2,000秒，同時還有定時取樣與背景取消。只能一筆一筆來的話，狀態與取消會被卡在換模型後面，所以：
  - 每筆指令帶主控台產生的隨機 `id` 與期限；結果一定要帶同一個 `id`，主控台依 `id` 叫醒對應的那個 `call_node()`，對不上的結果直接丟掉。
  - 代理每筆指令各開一條執行緒，長的不會擋住短的。
  - 代理記住最近1小時、最多256筆已執行的 `id` 與結果。同一個 `id` 再送來（網路重送）就直接回上次的結果，不重做一次副作用。
  - 超過期限沒回，`call_node()` 回504。之後才到的結果只記一筆紀錄，不再當成回應。
  - 取消是一筆獨立的指令，帶要取消的那個 `id`。
- **驗證**：
  - 代理通道用**專用的通道憑證**，不和管理網頁共用。管理者在網頁上換管理網頁的憑證時（`console/tls.py` 的 `generate_csr()` 會產新私鑰），通道憑證不受影響，代理就不會一起斷線。
  - 代理在加入時取得通道憑證的公鑰並釘住，之後只認這把。沿用現行 `curl --pinnedpubkey` 的做法，不准退回不驗證。
  - **通道憑證輪替**：主控台先產生下一把，經現有通道用目前這把的身分把新公鑰發給每台；代理同時信任新舊兩把，回報收到。所有在線機器都收到後才換上新的，舊的再保留30天。超過30天都沒上線的機器要重新加入。
  - 主控台照舊用節點權杖認代理。
- **代理伺服器**：連主控台時要照系統或指定的HTTPS代理伺服器走（企業常見）。連本機時繼續不走代理，這是現行的規則。
- **離線不排舊指令**：機器離線期間，主控台不累積一般指令。關機錯過的變更一律靠群組設定對齊補上，避免隔天開機才執行一個昨天的「停止」。
- **唯一的例外是安全指令**：停用、恢復、清除、撤銷身分這四種，存在主控台資料庫裡，機器下次連上時，在任何對齊之前先執行。
  - 每筆都有 `id`，重複執行結果相同（清除兩次和清除一次一樣）。
  - 送出之前管理者可以取消；後下的會覆蓋先下的（例如「恢復」會取消還沒送出的「停用」）。
  - 不設期限：機器遺失半年後才開機，照樣要清。
  - 代理執行完回報，主控台記下完成時間並寫稽核。
- **連線上限要改**：`tls.TLSServer` 現在是每個來源最多64條連線。企業的工作站走NAT或VPN時，幾百台看起來是同一個IP，第65台就會被拒。已驗證的代理通道要改成依節點計，只有未登入的請求維持依來源計。
- **規模上限**：主控台是每條連線一個執行緒。200台長輪詢是200條閒置執行緒，沒有問題；500台以上要改用非同步伺服器，到時再做。
- **對外只開通道**：遠端工作的筆電要從外面連回來時，代理通道和管理網頁要能分開聽不同的埠，對外只開代理通道那一個。

### 2. 群組設定與開機對齊

群組是新的一級物件：`id`、名稱、種類標籤（一般／教室／部門，核心只當顯示用）、設定、版本號（只增不減）、更新時間。

群組設定的欄位：

| 欄位 | 用途 |
|---|---|
| `models` | 要哪些模型。可以寫「自動」，由主控台依每台硬體挑版本，見第4點 |
| `profile` | 上下文、並行數、思考開關、取樣參數 |
| `locked` | 哪些項目使用者在本機不能改 |
| `reserve_user_gib` | 保留給使用者其他程式的記憶體 |
| `storage_root` | 模型與身分放哪裡（還原卡要指到不還原的磁碟） |
| `sources` | 模型可以從哪裡取得：同群組、內部鏡像、Hugging Face |
| `allowed_models` | 只准用哪些模型（空的就是不限）。強制點在代理，清單內容可由企業版模組產生 |
| `apply_at` | 立即、下次開機或指定時間 |
| `gpu_power_limit` | 顯示卡功耗上限（瓦）。空的就是不限，見第12點 |

對齊分成「準備」與「套用」兩段，代理分別記兩個版本：**已準備的版本**與**已套用的版本**。

1. 代理連上時送出這兩個版本。
2. 主控台有比較新的版本，就回傳整份設定與它的 `apply_at`。
3. **準備**（收到就做）：取得模型、核對sha256、以新設定做一次准入預檢。完成後更新「已準備的版本」，這一段不碰正在跑的服務。
4. **套用**（等到 `apply_at` 才做）：換上、鎖定。
   - 立即：準備完就套用。
   - 下次開機：代理下次啟動時套用。
   - 指定時間：以主控台的時鐘為準。主控台每次輪詢都回傳目前時間，代理用它算出和本機時鐘的差，不信任本機時鐘。
5. 每一步都回報狀態。失敗就停在那一步並回報原因，已在跑的服務不動（沿用現行換模型的失敗還原）。

這樣在上課中或上班時間發布新設定，也只會先準備好，不會提早換掉正在用的模型。群組總覽的「就緒」看已準備的版本，「已套用」看已套用的版本。

**鎖定的強制點在代理**：被鎖的項目，本機網頁與API一律拒絕修改。代理每次對齊時，也會把被改過的鎖定項目拉回群組設定的值。桌面App怎麼接上這支代理，見第11點。

**套用方式**：學校上課是「全部一起換」，企業推送是「一群一群換」。核心只提供「對這個群組套用」與「並行上限」兩個參數；一群一群換的順序與觀察期由企業版模組排。

### 3. 加入與身分

- **群組加入碼**：可用N次、有效T分鐘，加入時就放進指定群組。名稱可以用樣板（例 `A{01..20}`），或直接用主機名稱。加入碼只顯示一次，資料庫只存雜湊。
- **靜默安裝**：`install.ps1 -Console <網址> -JoinCodeFile <檔案> -DataDrive D:`，Linux與macOS的 `install.sh` 也比照。Intune、SCCM和映像派送都走這條。
  - **加入碼不准放在指令列**：會留在行程清單與派送紀錄裡，看得到的人在有效期間內就能拿去加入別的機器。只接受兩種方式：標準輸入，或回應檔。
  - 回應檔的權限只給SYSTEM與系統管理員，安裝程式讀完就刪掉。
  - 安裝程式看到 `-JoinCode` 參數一律拒絕，並說明改用哪一種方式。
  - 加入碼也不寫進環境變數。管理者在主控台看得到每個加入碼加入了哪些機器，可以隨時作廢，也可以限定只收某個網段來的加入。
- **開機就跑**：受管機器一律裝成開機自動啟動，不能只在使用者登入時才啟動，否則教室裡沒人登入的機器收不到設定。
  - Windows：`SYSTEM` 排程（`install.ps1` 系統管理員模式已有）。
  - Linux：以專用帳號 `xconsole` 執行，開機由systemd帶起它的使用者服務（linger）。不直接寫成系統服務的原因：代理用 `systemctl --user` 管模型服務、用 `systemd-run --user --scope` 讓編譯與產圖跳出代理的資源上限，這兩件事都要在那個帳號自己的systemd底下做。
  - **macOS：大量部署裝成LaunchDaemon**（`/Library/LaunchDaemons`，以隱藏帳號 `_xconsole` 執行）。「加一台機器」的一行指令仍是使用者的LaunchAgent，登入後才會啟動，開著機但沒人登入的教室Mac請用大量部署。代理啟動時實際向系統要一次Metal裝置，拿不到就不列GPU、模型改用CPU跑，機器頁的記憶體區寫明原因。
- **身分與複製偵測**：
  - 代理第一次啟動時產生節點身分，並記下這幾個識別碼：作業系統識別碼（Windows的MachineGuid、Linux的 `/etc/machine-id`）、SMBIOS UUID、系統碟序號，以及所有實體網卡的MAC。
  - **網卡不參與判定**：筆電在Wi-Fi、有線、USB擴充座之間切換，「主要網卡」就會變。MAC只記下來給管理者參考，變了也不影響身分。
  - **判定規則**：
    - SMBIOS UUID改變：視為換了一台機器（複製映像或硬碟搬到別台），丟掉舊身分、重新加入。
    - SMBIOS UUID沒變、只有作業系統識別碼改變：視為同一台重灌，保留身分，在畫面上註記。
    - 兩者都沒變：同一台。
  - 便宜主機板常見SMBIOS UUID全是F、全是0，或多台重複。遇到這種無效值，改用系統碟序號判定。
  - 需要重新加入但加入碼已經失效時，在本機畫面顯示「需要重新加入」。
  - 主控台看到同一個身分從兩組識別碼連進來時，兩台都標「疑似複製」並拒絕下指令。實作上看的是代理每次啟動產生的編號：正常重啟是舊的停了才有新的，兩個編號輪流出現就是兩台同時在跑。這一條也蓋住主機板識別碼本身就重複、或虛擬機器器複製時識別碼完全相同的情況。
  - Linux的product_uuid只有root讀得到：大量部署另裝一支root的開機服務，每次開機把它抄到 `/run`（不會跟著映像複製）給專用帳號讀；用一行指令裝的一般帳號讀不到，就改看系統碟序號。
- **還原卡接回**：身分存在 `storage_root`（不還原的磁碟）。如果還是遺失，要接回原來那一格只有兩條路，**都不能只靠SMBIOS UUID**，因為它不是秘密、可以照抄或偽造，靠它接回會重演2026-10-25審查重現的「重新安裝可以搶走已納管機器」：
  - **接回憑證**：加入時代理另外取得一張接回憑證，存在 `storage_root` 下另一個路徑。拿它來接回，主控台驗過後當場換發一張新的，舊的作廢，所以每張只能用一次。
  - **管理者核准**：沒有接回憑證的機器，宣稱要接回某一格時，會進入「待核准」清單。畫面列出新舊識別碼的差異，管理者（或那間教室的老師）按核准才接回；不核准就當成新機器。
  - 這兩條都要群組有開「允許接回」，預設關閉。

### 4. 混合機型自動挑版本

- 主控台依每台回報的硬體分類（獨立顯示卡NVIDIA／AMD、`unified_split`、`unified_single`、純CPU）與記憶體大小，用 `recommend.py` 和准入同一條公式，替每台挑引擎與量化。
- 群組設定頁依機型分類列出：會拿到哪個檔、大概多快（估算，畫面寫明），可依機型覆寫。
- 中國來源的模型在這張表與所有出現模型名稱的地方，一律醒目標示「中國來源」；只標示，不自動排除（清單 #27）。
- 放不下的機器一律給替代方案：改小一級的模型、放硬碟、縮上下文。不能只回「記憶體不夠」，這條沿用「一般人的電腦都要跑得起」。
- **推理引擎預先編好**：Windows CUDA／Vulkan、Linux x64 CUDA、macOS Metal用官方正式版。官方沒有的平台（Jetson與GB10的aarch64 CUDA），在群組裡挑一台編一次，產物經核對後放進內部鏡像給同平台的機器。不要讓20台各自編譯。

### 5. 模型分發

取得模型的順序：同群組已核對過的機器，然後是內部鏡像，最後才是Hugging Face（要 `sources` 有允許）。

- **工作站之間互傳**：
  - 由接收的機器去跟已有模型的機器拿，走代理的HTTPS。每次傳送由主控台發一張60秒、只能用一次的票證，不用長效權杖，符合機密處理鐵則。
  - 支援續傳，每個檔都核對sha256。sha256以Hugging Face公布的LFS雜湊為準。
- **連得到才互傳**：代理改成主動連回，就是因為工作站通常不收連入的連線。互傳需要「送的那台」收連入，所以：
  - 群組有開同群組互傳時，代理另外聽一個**只給互傳用的埠**（預設9403），只收本機所在網段：代理自己比對連線者的位址，Windows另由代理加防火牆規則 `-RemoteAddress LocalSubnet`（套用到所有網路設定檔，包含公用網路；安裝時還不知道群組設定，所以由代理依群組設定開關，不放在安裝程式）。這個埠只開放下載存放區裡核對過sha256的模型檔，而且一定要帶票證。群組關掉互傳，監聽與防火牆規則一起移除。
  - 主控台在排程前請各台互相試連一次，只把連得到的機器排進樹裡。
  - 連不到的機器，例如在家的筆電、開了AP隔離（裝置之間互相連不到）的Wi-Fi、不同網段，一律改從內部鏡像拿，走的是對外HTTPS。
- **排程**：主控台排成樹狀，拿到的機器再傳給下一台，每台同時最多送2份。

  **估算**（1 GbE、實際約110 MB/s、20 GB的模型、20台都在同網段且互相連得到）：
  - 全部從同一台拉：約61分鐘。
  - 樹狀傳：每一輪約3分鐘，5輪到齊，約15分鐘。

  連不到、改走內部鏡像的機器不在這個估算裡。實際數字要在第二期實測後改寫。
- **內部鏡像**：主控台或指定的一台機器先從Hugging Face取得，工作站一律從內部拿。適用於企業代理伺服器擋外網、或學校外網頻寬小的情況。
- **限速與時段**：可設上課或上班時段的頻寬上限。
- **筆電**：用電池時不下載、不載入大模型；網路是Windows的計費連線時不下載。

### 6. 工作站准入

- 底線加上群組的 `reserve_user_gib`。准入仍算「載下去之後最壞剩多少」，而且是用當下的可用記憶體算，使用者已經開著的程式本來就會算進去。
- **使用者優先**（工作站新增）：模型跑著的時候，如果使用者的程式把可用記憶體壓到底線以下，代理可以先卸載模型並通知使用者，不讓整台卡死。群組可以選「卸載模型」或「不動」，工作站預設卸載。
- Windows、macOS沿用現行的軟底線。

### 7. 群組總覽

- 每台一張卡，顯示狀態：就緒、準備中（下載x%）、放不下（建議改用X）、離線（上次連線時間）、設定不同、需要重新加入、疑似複製。
- 標題列顯示「N／M台就緒」與下一步。
- 輪詢只換有變的數字，照 `ui-no-flicker` 的做法，不整頁重建。
- 卡片排列方式由群組種類決定。核心提供格狀排列；座位圖由企業版模組的教育包提供。
- **導覽**：只有本機一台時（個人版），畫面完全不變。主控台有群組時，「概覽」換成群組總覽，點進群組就是上面的群組頁。

### 8. 多帳號與角色

- 角色分三種：管理者、維運（可以換模型、重啟、套用群組，不能加機器、不能改帳號）、檢視。每個帳號可以限定只能管哪些群組。老師就是「只管自己那間的維運」。
- 授權檢查放在核心，所有API都依目前帳號的角色與群組範圍判斷，物件層一律驗。單一登入、以網域群組對應角色，由企業版模組提供。

### 9. 即時問題回報

xConsole目前沒有這項，全域規則要求每套交付的系統都要有，而且多工作站情境最需要（學生、員工看到數字怪怪的要能當下回報）。

- 每頁一顆回報鈕，數字旁邊一顆「回報數字有誤」。
- 回報時系統自動帶入機器、群組、頁面與當下狀態。
- 管理者與云碩收件人收得到通知，緊急件逾時會催辦。
- 通知名單或郵件伺服器沒設好，管理頁要顯示警示。

參考實作是xIR `app/report.py`。

### 11. 桌面App接上受管的系統代理

現行桌面App每次啟動都自己帶起一支私有代理（`--bind 127.0.0.1`、`XCONSOLE_DESKTOP=1`，資料放在App自己的資料夾），並把它登記進App自己的主控台（`install/setup_local.py`）。受管機器上真正受管的，是以SYSTEM（或Linux、macOS的專用帳號）執行的那支，認證資料在權限保護的 `ProgramData`。結果是App看到、操作到的是另一支不受管的代理。

改法：

- **啟動時先判斷這台有沒有受管**：有受管的系統代理，就不再帶起私有代理，改接系統代理；沒有就照現在的做法，也就是個人版。
- **本機使用者通道**：系統代理另外開一個只給本機使用者的通道，**只開放使用者層的操作**：看狀態、對話用的模型端點、看哪些項目被鎖、送出求救。換模型、改設定、加入或退出群組都不在這個通道上。
  - Windows：具名管道，ACL只給互動式登入的使用者；伺服端取得連線者身分並寫進稽核。
  - Linux、macOS：Unix socket。socket檔開0666，用 `SO_PEERCRED`／`LOCAL_PEERCRED` 取得連線者，只放行坐在電腦前的人（Linux看logind座位的 `ACTIVE_UID`、macOS看 `/dev/console` 的擁有者）。原本規劃只給 `xconsole` 群組，但教室裡每個學生的帳號都要加進群組，管理不來，而且專用帳號的群組不該給學生。
  - 標準函式庫就做得到（`multiprocessing.connection` 支援具名管道，`socket` 支援Unix socket），不新增相依。
- **對話紀錄仍存在每位使用者自己的App資料夾**。管理端要清除對話時，系統代理把清除指令留在這個通道上；App開著就立刻執行，沒開就等下次開啟時執行，執行完回報則數（清單 #22）。
- **App的本機主控台照樣強制鎖定**：鎖定清單從通道讀，被鎖的設定在畫面上停用，API也拒絕。

### 12. 顯示卡功耗上限

教育包要的「上課功耗上限」，強制點必須在核心，因為模組不能在代理上執行程式碼。現在代理只會讀功耗，沒有設定功耗的功能。

- 群組設定欄位 `gpu_power_limit`（瓦）。代理驗證數值在這張卡允許的範圍內，套用後回報實際值。
- NVIDIA：`nvidia-smi -pl`。系統代理有權限，個人版的私有代理沒有，所以只對受管機器有效。
- AMD獨立顯示卡：依驅動支援的方式設定。AMD APU與Apple Silicon不支援，回報「這台不支援」，畫面照實標示，不假裝有效。
- 欄位清空或機器退出群組時，還原成原廠預設值。
- 企業版模組只負責「什麼時段設多少」與畫面。

原則：**會影響安全的強制點一律在公開核心**（代理只有一支，強制邏輯可被審查）；**政策內容、場景流程與管理畫面在閉源模組**。模組不能在代理上執行任何程式碼。

| 混合機型自動挑版本、預編引擎、工作站互傳、內部鏡像 | 核心 |

## 五、擴充合約（核心API第1版）

### 載入

1. 主控台啟動時找 `<安裝目錄>/enterprise/`，或設定檔指定的路徑（只是路徑，不是機密）。
2. 先讀 `manifest.json`，內含模組版本、`core_api`，以及每個檔的sha256。
3. 用核心內建的云碩公鑰，以Ed25519驗 `manifest.sig`（主控台已相依 `cryptography`）。
4. 逐檔核對sha256。
5. 檢查目錄與檔案只有系統管理員能寫（Windows檢查ACL，Linux與macOS檢查擁有者與權限）。
6. 確認 `core_api` 相容。
7. 全部通過才import。

任一步失敗都以開源核心啟動（等同沒有企業版），並在「設定」顯示原因與修法，不可默默失效。授權（客戶、席次、到期日、功能）由模組自己驗，核心不碰。

公開核心可以被人改掉驗證步驟，所以簽章的作用是**防止被竄改的模組被載入**。它不是防盜版機制，對客戶與文件都照這樣說明。

### 擴充點

模組的入口是 `register(api)`，`api` 只開放以下幾類：

| 擴充點 | 內容 | 核心負責 |
|---|---|---|
| `api.route(method, pattern, handler, role, scope)` | 只能掛在 `/api/ent/` 底下；`scope` 必填，說明這個請求碰的是哪個群組 | 登入、角色與群組範圍、CSRF、本文大小、統一錯誤處理、稽核 |
| `api.static(dir)` | 前端檔案掛在 `/ent/static/`，頁面以 `XC.registerPage()` 註冊 | CSP `script-src 'self'` 照舊 |
| `api.auth_provider(provider)` | 單一登入，回傳身分與網域群組 | 建立票證、處理登出與逾時 |
| `api.role_mapper(fn)` | 網域群組對應到角色與群組範圍 | 授權判斷 |
| `api.group_fields(schema)` | 群組設定加欄位（只能是資料） | 驗證格式；能強制的只有第三節第2點列出的核心欄位 |
| `api.group_layout(name, js)` | 群組總覽的排列方式（例如座位圖） | 資料與更新 |
| `api.apply_plan(fn)` | 決定一次套用哪些群組、間隔多久 | 實際套用與並行上限 |
| `api.on(event, fn)` | 事件：上線、離線、准入擋下、對齊結果、問題回報 | 事件內容先過遮罩 |
| `api.report_section(fn)` | 在使用報告加章節 | 報告產生 |
| `api.store(namespace)` | 模組自己的資料表 | AES-256-GCM加密輔助、`enc:v1:` 前綴 |
| `api.audit(action, target, ok, detail)` | 寫稽核 | 寫入前遮罩 |

**群組範圍由核心在進handler之前檢查，不交給模組自己判斷。** `scope` 只能是下面三種之一：

| `scope` | 意思 | 核心怎麼查 |
|---|---|---|
| `api.scope.path("room_id")`、`api.scope.body("group_id")` | 群組編號在網址或本文的某個欄位 | 取出群組編號，確認目前帳號能管這個群組 |
| `api.scope.obj("edu_templates", "id")` | 請求碰的是模組自己的某筆資料 | 用 `api.store` 查出那筆資料屬於哪個群組，再確認同上；查不到就回404 |
| `api.scope.GLOBAL` | 不屬於任何群組（授權、單一登入設定等） | 只允許「管理者（全部群組）」 |

- `api.store` 的每張資料表都要有 `group_id` 欄位（全域資料填 `null`）。模組查詢時，核心自動加上目前帳號的群組範圍。
- 列表類的端點只會拿到範圍內的資料，模組拿不到也送不出別的群組的資料。
- 沒帶 `scope` 的路由，註冊時就失敗。

公開repo放一個測試用的假模組（以測試金鑰簽章），並加 `test/test_module_contract.py`：核心任何改動只要破壞上面的合約就會失敗。合約有不相容的變更時，`core_api` 加一，並保留舊版一個正式版週期。

## 六、資安

`docs/THREAT_MODEL.md` 要新增五條信任邊界，`SECURITY_PLAN.md` 一併更新（已完成：威脅模型v1.6、安全計畫v1.2。威脅模型原本就用掉了B5～B12，這裡的B5、B6、B7、B8、B9在威脅模型裡分別是B13、B14、B12、B7、B15）：

| 邊界 | 主要威脅 | 控制 |
|---|---|---|
| B5代理 → 主控台通道 | 假主控台下指令；偷節點權杖冒充；大量連線拖垮；網路重送造成重複執行；換憑證讓全部機器斷線 | 釘專用通道憑證、依協定輪替；權杖密封存放；指令編號加去重；已驗證通道依節點計連線數；未驗證依來源計 |
| B6工作站互傳 | 拿到不該拿的檔案；傳來被竄改的模型；互傳埠被當成入侵點 | 60秒一次性票證、只限該檔；逐檔sha256；只能讀 `storage_root` 下的模型；互傳埠只收本機網段，群組關閉互傳就移除 |
| B7模組載入 | 被換掉的模組在主控台執行任意程式碼；模組忘了檢查群組範圍 | Ed25519簽章、逐檔sha256、檔案權限檢查、`core_api` 相容檢查；路由一律宣告 `scope`，由核心檢查 |
| B8群組加入 | 撿到加入碼塞進惡意機器；從指令列或派送紀錄撿到加入碼；複製機搶身分；偽造SMBIOS UUID搶走既有那一格 | 加入碼限次數、時限、網段，只存雜湊、可作廢，不准放指令列；以SMBIOS與作業系統識別碼判定複製；接回只認一次性接回憑證或管理者核准 |
| B9本機使用者 → 系統代理 | 學生或員工經本機通道換模型、改設定、解除鎖定 | 通道只開放使用者層操作；具名管道ACL、Unix socket權限；連線者身分寫稽核 |

單一登入的OAuth回跳邊界在企業版模組的威脅模型裡寫。交付前兩個repo都要跑 `check-compliance.sh --level 中`、`check-https.sh`、`audit-secrets.sh`，有「缺」或「高風險」就不算完成。
